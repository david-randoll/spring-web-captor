Publication and merge are separate gates

These are draft PRs while upstream artifacts are absent. A red dependency-resolution check before publication is not approval to bypass CI. After every upstream publication, rerun the dependent checks. Do not merge a consumer while its published-dependency gate or clean build is red.

Credentials and registries

No source-checkout token is required for the Connect release. Grant each consuming repository Actions access to its private dependency packages, as David will configure manually. CI uses the job token when no dedicated package-read secret is present. Missing packages or missing read grants will still stop CI.

Cross-repository policy and decision checks remain enabled. Each Maven parent now publishes a release-contracts ZIP alongside its normal artifacts. Cloud resolves those archives at the exact versions in its POM instead of cloning private source repositories. Publish the parent and attached archive together; a missing or incomplete archive fails the check.

  • Engine: CAPTOR_PACKAGES_TOKEN reads Captor; its own GITHUB_TOKEN publishes engine/UI.
  • Auth and Connect: WEAVRIC_PACKAGES_TOKEN reads upstream private packages, falling back to the job token if Actions access is configured.
  • Cloud: the same read credential must cover engine, Auth, UI Builder, Connect and Captor.
  • Local Maven commands use checked-in settings files with environment references only. Never paste token values into a PR or command history.
  • Local npm needs @weavric:registry=https://npm.pkg.github.com and a user-level authenticated npm configuration. The repository .npmrc contains only the registry URL.
New workflows cannot bootstrap themselves

GitHub may require a workflow to exist on the default branch before manual dispatch. Existing engine and Auth Java workflow paths can be dispatched against the reviewed release ref. Connect's new backend workflow and Auth's new frontend workflow may need a small separately reviewed workflow-only bootstrap PR, or the equivalent local commands below. Do not merge the whole consumer prematurely just to enable a publish button.

Connect (from its reviewed release checkout):
mvn -B -ntp -s .mvn/settings-release.xml -pl connect-backend -am clean verify
mvn -B -ntp -s .mvn/settings-release.xml -pl connect-backend -am org.apache.maven.plugins:maven-enforcer-plugin:3.5.0:enforce -Drules=requireReleaseDeps,requireReleaseVersion
mvn -B -ntp -s .mvn/settings-release.xml -pl connect-backend -am deploy -DskipTests -DdeployAtEnd=true

Auth frontend (from its reviewed release checkout):
npm ci --prefix console
npm run build --prefix clients/admin-ui
npm test --prefix clients/admin-ui
npm ci --prefix clients/auth-flow-client
npm run verify --prefix clients/auth-flow-client
npm publish ./clients/auth-flow-client --registry=https://npm.pkg.github.com
npm publish ./clients/admin-ui --registry=https://npm.pkg.github.com

Only run publication commands after review and all prerequisite verification. For Connect set GITHUB_ACTOR, GITHUB_TOKEN (write access to Connect packages) and PACKAGES_READ_TOKEN (read access to engine, Auth and Captor) in the process environment using your credential manager.

Finalize application npm dependencies after publication

The packages do not exist yet, so their registry lockfiles cannot honestly be generated now. Each app PR contains scripts/finalize-published-ui.mjs. It lists replacements by default, verifies every exact version in GitHub Packages before modifying files with --apply, and restores the original manifest/lock if npm fails.

node scripts/finalize-published-ui.mjs
node scripts/finalize-published-ui.mjs --apply
# Review and commit the generated package.json and package-lock.json changes.
# Then run npm ci, unit tests and build in frontend/ (Connect) or admin/ (Cloud).

Keep the PR draft until this is complete. Do not hand-invent package integrity hashes or mark a local file dependency as published.
